# AI-generated personal itineraries

**Status:** design approved (mockup: https://claude.ai/code/artifact/ac1113aa-16c9-408f-aa36-44179f43ff00),
spec pending implementation plan(s).

## Why

Users browsing the map see many individual places but have no way to ask "what should I do with the
time I have" — no route composition, no time-boxed theme-based planning. Product direction (from user
conversation): let a user describe what they want in their own words ("1h à Santa Teresa, focus street
art, avec pause déjeuner") and get back a real, walkable route built from the app's own verified places.

## Scope

**In scope (v1):**
- A personal "Mes itinéraires" list, per user account (existing Auth already gates account features).
- Free-text chat creation flow: describe constraints, get a proposed itinerary back inline in the
  conversation, open it as a full detail view.
- Itinerary composition draws **only from places already in this app's grounded database** — the LLM
  sequences and times real, verified places; it never invents a place.
- One explicitly-marked exception: a single optional "meal break" slot, generated by the LLM from its
  own general knowledge (not the grounded database), visually and textually marked as an unverified
  suggestion — never given the same "✓ sources vérifiées" trust signal the rest of the app uses for
  real content. This is the sole controlled entry point for ungrounded content in this feature.
- Entry points: a header icon on `Map.tsx` (alongside the existing Settings gear), an entry in
  `Settings.tsx`, and (placement TBD at implementation time) an "add to itinerary" action from
  `PlaceDetail.tsx`.

**Explicitly out of scope for v1 (deferred, not decided now):**
- Community/shared itineraries — browsing itineraries other users created. A separate, later
  sub-project (discovery UI, moderation, ranking — real scope on its own).
- Restaurant/activity recommendations beyond the single meal-break slot described above.
- Turn-by-turn navigation/directions between stops (this feature produces a sequenced list with
  estimated walking times, not live directions — see "Directions" in After this plan).
- Editing an itinerary after generation beyond regenerating it (no manual drag-to-reorder in v1).

## Screens (mockup reference)

Three screens, all in the app's existing light/warm theme (cream/terracotta, Playfair Display + Inter)
— **not** `PlaceDetail`'s dark immersive theme, which stays reserved for audio playback:

1. **Mes itinéraires** (list) — a prominent "Créer un itinéraire" button, then cards per saved
   itinerary (title, duration, stop count).
2. **Création par chat** — a normal chat UI (assistant bubble, user bubble, free-text input). When the
   assistant proposes an itinerary, it renders as a compact inline card inside its own chat bubble
   (title, duration, numbered stop list, the meal-break slot visually distinct/italicized/marked
   unverified) with a "Voir l'itinéraire complet" button.
3. **Détail de l'itinéraire** — a vertical timeline: each stop is a numbered terracotta badge + place
   name + time-on-site, connected by a walking-time indicator to the next stop. The meal-break slot
   (if present) breaks this pattern deliberately: a dashed-border badge instead of a solid numbered one,
   italic muted text, and an explicit "suggestion de l'IA, non vérifiée" caption — this is not
   decorative, it is the feature's one real trust-distinction requirement carried into the UI.

## Backend: new domain concept (authorship note)

This feature needs a new domain concept — an `Itinerary` aggregate (ordered stops, each either a real
`Place` reference + time-on-site, or the one unverified meal-break slot; overall duration; owning user).
Per this project's standing authorship split (`CLAUDE.md`): **`internal/domain/` and `internal/ports/`
are hand-written by the founder** — this spec describes the *shape* of that concept for planning
purposes only, and does not authorize an implementation plan to write those files. A future
implementation plan for the backend piece scopes its own tasks starting from `internal/adapters/`
outward (the HTTP route, the Postgres repository, the Claude API-calling generator adapter), the same
split already used for every backend feature on this project — the actual `Itinerary`/`ItineraryStop`
domain types and the `ItineraryRepository`/`ItineraryGenerator` port interfaces are the founder's own to
write before that adapter work can begin.

**LLM call shape (for the founder's own port design to target, not prescribed here):** the generator is
called with the user's free-text request plus a list of real candidate places (name, category,
coordinates, neighborhood — drawn from the same grounded database everything else in this app uses) and
must return a subset of those places, ordered, with estimated time-on-site per stop, plus optionally one
meal-break suggestion clearly tagged as such in the response shape (so the mobile client can render it
distinctly without any string-sniffing). Provider: Claude API (Anthropic), consistent with the rest of
this project's tooling — model choice and prompt design belong in the implementation plan, not this
design doc.

## Mobile: chat + detail screens

Three new screens (`ItinerariesList`, `ItineraryChat` or similar, `ItineraryDetail`) added to the
existing single-stack navigation (`AppStackParamList`) — no tab bar introduced, per explicit direction
already given for this feature. Consumes whatever HTTP contract the backend sub-project defines; no
client-side LLM calls (matches this project's pattern of the backend, not the mobile client, holding
API keys and provider integration).

## Testing

- Backend: adapter-level tests for the Claude-calling generator (mocked LLM responses, following the
  existing `awspolly`/`elevenlabs` adapter test pattern — fake the external client, not the network) and
  the HTTP route, once the founder's own domain/ports work exists to build against.
- Mobile: pure logic (parsing the itinerary response shape, distinguishing the meal-break slot) gets
  Jest coverage per this project's existing convention; the three screens themselves are not
  component-tested (matches every other screen in this app).

## After this plan (explicitly deferred)

- Community/shared itineraries.
- Turn-by-turn directions between stops (Google Maps Directions API, or a deep link out to the phone's
  own maps app — a real cost/integration decision not made here).
- Editing/reordering an itinerary manually after generation.
- Broader ungrounded recommendations beyond the single meal-break slot.
- Street art in Santa Teresa (a separate, already-identified content-curation task — no existing source
  captures it automatically; requires a human to compile a real, sourced list, same rule as all
  narration content in this project).
